# Coding Conventions

> **Status:** Canonical code-shape contract.  
> This file owns naming, organization, and code-style decisions. Architecture flows live in [architecture](architecture.md), enforceable boundaries in [rules](rules.md), and the agent process in [workflow](workflow.md). See [AGENTS.md](../AGENTS.md) for document precedence.

> **Project context:** Domain names, event names, tables, and paths in examples are illustrative. Apply the naming rules to actual pos-icool concepts; do not create sample modules from this document. The [project profile](../docs/project-profile.md) records the three apps, PostgreSQL, and the absence of migrations.

---

# 1. Purpose

The purpose of this document is to keep code generated by humans and AI/Coding Agents consistent across the repository.

This document answers questions such as:

```text
How should files be named?

How should classes be named?

When should we use Service vs UseCase?

How should Repository Ports and implementations be named?

How should ORM entities be named?

How should DTOs be named?

How should Events be named and versioned?

How should errors and error codes be named?

How should tests and migrations be named?

How should imports and exports be organized?
```

Consistency is important because this repository is expected to evolve through many modules, contributors, and agents.

---

# 2. General Naming Principles

Use names that communicate business intent.

Prefer:

```text
PayInvoiceUseCase
FindOpenInvoiceByRoom
InvoiceAlreadyPaidError
PromotionPricingPort
TypeOrmInvoiceRepository
```

Avoid vague names:

```text
Manager
Helper
UtilsService
CommonService
DataService
ProcessService
BaseManager
GenericHandler
```

A name should answer:

```text
What does this thing represent?

What responsibility does it own?

Which business capability does it belong to?
```

---

# 3. Language

All source code identifiers MUST use English.

Use English for:

```text
Class names
Function names
Variable names
File names
Folder names
DTO names
Event names
Error names
Database migration names
Test descriptions where practical
```

Business display text may use the required product language.

Example:

```ts
export const SERVICE_FEE_NAME = 'Phí phục vụ';
```

is acceptable when the string is a business-facing value.

Do not use Vietnamese identifiers such as:

```ts
tinhTongTien()
hoaDon
khachHang
```

Prefer:

```ts
calculateTotal()
invoice
member
```

Use:

```text
kebab-case
```

for source files.

Examples:

```text
pay-invoice.use-case.ts

invoice-response.dto.ts
```

Do not use:

```text
PascalCase.ts
camelCase.ts
snake_case.ts
```

unless a tool/framework requires it.

for folders.

# 7. Interface Naming

Do not use `I` prefixes.

Avoid:

```ts
IInvoiceRepository
IPaymentGateway
ICachePort
```

Prefer:

```ts
InvoiceRepository
PaymentGateway
CachePort
```

Interfaces should describe capability, not implementation.

# 8. Type Naming

Use `PascalCase`.

Examples:

```ts
InvoiceStatus

PaymentMethod

CreateInvoiceInput

CreateInvoiceResult

InvoiceListItem

EventEnvelope<T>
```

Avoid names that hide meaning:

```ts
Data
Payload
ResultData
Temp
Info
```

unless the surrounding context makes them precise.

---

# 9. Enum Naming

Enum names use singular `PascalCase`.

Example:

```ts
export enum InvoiceStatus {
  OPEN = 'OPEN',
  PAID = 'PAID',
  CANCELLED = 'CANCELLED',
}
```

Enum members use:

```text
UPPER_SNAKE_CASE
```

unless external contracts require another format.

---

# 10. Constant Naming

Use:

```text
UPPER_SNAKE_CASE
```

for true constants.

Examples:

```ts
export const SERVICE_FEE_CODE = 'SERVICE_FEE';

export const DEFAULT_PAGE_SIZE = 20;

export const MAX_PAGE_SIZE = 100;
```

Do not use uppercase naming for ordinary runtime variables.

---

# 11. Symbol / Injection Token Naming

Injection tokens should be explicit constants.

Example:

```ts
export const INVOICE_REPOSITORY =
  Symbol('INVOICE_REPOSITORY');
```

Prefer token names:

```text
<NAME>_REPOSITORY
<NAME>_PORT
<NAME>_GATEWAY
UNIT_OF_WORK
OUTBOX
CACHE_PORT
```

Do not create anonymous `Symbol()` values inline inside module definitions.

Keep tokens near the corresponding abstraction.

---

# 12. Boolean Naming

Boolean variables/functions should read naturally.

Prefer:

```ts
isPaid
isActive
hasPermission
canRefund
shouldRetry
```

Avoid:

```ts
paid
activeFlag
permissionCheck
retryValue
```

---

# 13. Function Naming

Functions should use verbs.

Examples:

```text
create
pay
cancel
close
calculate
validate
find
load
save
publish
invalidate
map
```

Query-like functions should communicate what is returned.

Examples:

```ts
findById()

findForUpdate()

findOpenInvoiceByRoom()

getInvoiceSummary()

listInvoices()
```

Avoid excessive `handle()` methods unless implementing a framework-defined handler abstraction.


Examples:


```ts
InvoiceOrmEntity
```

# 16. Persistence Mapper Files

Use:

```text
<name>.mapper.ts
```

Class names:

```ts
InvoiceMapper
PaymentMapper
```

Example:

```text
modules/invoice/infrastructure/persistence/typeorm/mappers/
invoice.mapper.ts
```

Mapper methods should normally use:

```ts
toDomain()

toPersistence()
```

Example:

```ts
export class InvoiceMapper {
  static toDomain(
    entity: InvoiceOrmEntity,
  ): Invoice {
    // ...
  }

  static toPersistence(
    invoice: Invoice,
  ): InvoiceOrmEntity {
    // ...
  }
}
```

# 17. Repository Port Naming

Name a persistence port by what its callers can do:

```text
<business-object>.repository.ts       # writes, or a small cohesive read/write contract
<business-object>-read.repository.ts  # reads only
<specific-result>.query.ts            # a distinct reporting or projection query
```

Match the file, interface, and injection token:

```text
group.repository.ts          -> GroupRepository     -> GROUP_REPOSITORY
card-read.repository.ts      -> CardReadRepository  -> CARD_READ_REPOSITORY
```

Use `Repository` for an aggregate write contract or a small CRUD contract that also reads. Use `ReadRepository` or a specific `Query` for a read-only contract. Do not split a cohesive small contract merely to make the names symmetrical; split when the read and write responsibilities have different consumers or persistence needs.

Example write port:

```ts
export interface InvoiceRepository {
  // ...
}
```

Injection token:

```ts
export const INVOICE_REPOSITORY =
  Symbol('INVOICE_REPOSITORY');
```

Keep the Port in the owning module's Domain or Application layer according to dependency needs.

Preferred default:

```text
domain/repositories/
```

when the repository is part of Aggregate persistence semantics.

---

# 18. Repository Implementation Naming

Keep TypeORM implementations under the owning module's `infrastructure/persistence/typeorm/repositories/` directory. Match the port's responsibility:

```text
typeorm-<business-object>.repository.ts
typeorm-<business-object>-read.repository.ts
typeorm-<specific-result>.query.ts
```

Examples:

```text
group.repository.ts      -> typeorm-group.repository.ts      -> TypeOrmGroupRepository
card-read.repository.ts  -> typeorm-card-read.repository.ts  -> TypeOrmCardReadRepository
```

`persistence` names the infrastructure folder, not a class suffix. `Directory` does not distinguish reads from writes; do not use either suffix for new ports or adapters. Existing names are migration debt to correct in the owning module's refactor slice, including DI tokens, imports, and affected tests.

Do not name persistence implementations:

```text
InvoiceRepositoryImpl
InvoiceRepo
InvoiceRepositoryV2
```

unless required during migration.

---

# 19. Read Repository Naming

Read-side abstractions must make their role explicit. Prefer a read repository for ordinary lookups and a specific query for reporting or a specialized projection.

Examples:

```text
invoice-read.repository.ts
invoice-list.query.ts
daily-sales.query.ts
revenue-by-store.query.ts
```

Possible classes:

```ts
InvoiceReadRepository
InvoiceListQuery
DailySalesQuery
RevenueByStoreQuery
```

Do not overload Aggregate repositories with reporting/listing methods unrelated to Aggregate persistence.

# 20. Use Case Naming

For explicit write-side application operations, prefer:

```text
<verb>-<business-object>.use-case.ts
```

Examples:

```text
create-invoice.use-case.ts
pay-invoice.use-case.ts
cancel-invoice.use-case.ts
close-shift.use-case.ts
```

Class names:

```ts
CreateInvoiceUseCase
PayInvoiceUseCase
CancelInvoiceUseCase
CloseShiftUseCase
```

Use `UseCase` when the class represents one explicit application operation.

---

# 21. Application Service Naming

Use `Service` when the class exposes a cohesive set of application capabilities that naturally belong together and a dedicated Use Case per operation would add little value.

Example:

```ts
MemberLookupService
```

Do not create large generic services such as:

```text
InvoiceService
```

containing dozens of unrelated write/read operations.

For complex business modules, explicit use cases are preferred.

---

# 22. Command Naming

If Commands are used, name them:

```text
<verb>-<business-object>.command.ts
```

Example:

```text
pay-invoice.command.ts
```

Class/type:

```ts
PayInvoiceCommand
```

Commands should represent intent.

Do not use Commands as generic DTO replacements everywhere.


Prefer explicit input types:


or Commands/Queries when those abstractions are already used.

```text

```

```text
CreateInvoiceInput
```

They may initially share similar fields but are different contracts.

# 28. Response DTO Naming

Response DTO files:

```text
<resource>.response.dto.ts
```

or:

```text
<action>.response.dto.ts
```

Examples:

```text
invoice.response.dto.ts
invoice-detail.response.dto.ts
pay-invoice.response.dto.ts
```

Classes:

```ts
InvoiceResponseDto
InvoiceDetailResponseDto
PayInvoiceResponseDto
```

Do not suffix every nested response object with `Dto` if a simple exported type provides better readability.

These types are the `data` payload. The HTTP body is `{ data, errorCode, message, status }`, plus `metadata` only for a paginated API. See `docs/project-profile.md`.

```ts

```

# 30. Facade Naming

```ts
PromotionFacade
```


```ts
InvoicePricingService
```


File:


# 36. Kafka Topic Naming

Topic naming must be defined intentionally and centrally.

Recommended general format:

```text
<environment?>.<system>.<domain>.<purpose>
```

or another project-wide convention.

Examples might look like:

```text
ipos.invoice.events
central.member.events
kpos.shift.events
```

Do not hard-code topic strings across business code.

Topic names belong to messaging infrastructure/configuration.

# 37. Event Envelope Naming

Use a common generic type where appropriate:

```ts
export interface EventEnvelope<TPayload> {
  eventId: string;
  eventType: string;
  aggregateId: string;
  occurredAt: string;
  correlationId?: string;
  causationId?: string;
  source: string;
  version: number;
  payload: TPayload;
}
```

Use stable metadata names across all Integration Events.

# 38. Error Class Naming

Domain/Application errors should use:

```text
<Problem>DescriptionError
```

Examples:

```ts
InvoiceAlreadyPaidError
InvoiceNotFoundError
PromotionNotApplicableError
ShiftAlreadyClosedError
```

Avoid generic names:

```text
BusinessError
ValidationError
ProcessError
SomethingWrongError
```

unless they are meaningful base classes.

Errors extending the shared base declare `readonly category = ErrorCategory.<Category>`. Choose the business meaning, not an HTTP status name. `ValidationException` uses `BadInput`; invariant failures normally use `BusinessRule` or `Conflict`; absence uses `NotFound`. Presentation performs the HTTP mapping.

---

# 39. Error Code Naming

External/application error codes use:

```text
UPPER_SNAKE_CASE
```

Examples:

```text
INVOICE_ALREADY_PAID
INVOICE_NOT_FOUND
PROMOTION_NOT_APPLICABLE
SHIFT_ALREADY_CLOSED
```

These names identify domain error classes. They are not HTTP body fields. The body uses `errorCode` and `message` for the same safe client text, plus `data` and `status`. See `docs/project-profile.md`.

Do not casually rename a domain error class that callers already depend on.

---

# 40. Exception Mapper Naming

Presentation exception mapper:

```text
<transport>.exception-mapper.ts
```

or module-specific:

```text
invoice.exception-mapper.ts
```

Examples:

```ts
HttpExceptionMapper
InvoiceExceptionMapper
```

Prefer one coherent mapping mechanism over scattered `instanceof` checks in every controller.

---

# 41. Value Object Naming

Value Object files use the concept name:

```text
money.ts
phone-number.ts
invoice-number.ts
percentage.ts
```

Classes:

```ts
Money
PhoneNumber
InvoiceNumber
Percentage
```

Do not suffix every Value Object with `ValueObject` unless ambiguity requires it.

---

# 42. Factory Naming

Use static factory methods when creation requires validation/invariants.

Examples:

```ts
Invoice.create(...)
Payment.create(...)
Money.from(...)
```

Prefer:

```text
create
from
reconstitute
```

with clear semantics.

Possible convention:

```text
create()
    for new business objects

reconstitute()
    for restoring persisted Domain state
```

Do not use constructors as uncontrolled public mutation points when invariants must be enforced.

---

# 43. Private Constructors

Domain Entities/Value Objects MAY use private constructors when factories must protect invariants.

Example:

```ts
export class Money {
  private constructor(
    private readonly value: number,
  ) {}

  static from(value: number): Money {
    // validation
    return new Money(value);
  }
}
```

Do not force private constructors on simple models where they add no value.

---

# 44. Property Visibility

Prefer explicit visibility where it improves Domain safety.

Use:

```text
private
protected
readonly
```

when mutation should be controlled.

Avoid exposing mutable arrays directly.

Prefer:

```ts
get payments(): readonly Payment[] {
  return this._payments;
}
```

when Domain invariants depend on controlling collection mutation.

---

# 45. Nullability

Avoid ambiguous null semantics.

Use:

```text
undefined
```

for optional in-memory values when practical.

Use:

```text
null
```

when the database/API contract explicitly represents null.

Do not mix `null` and `undefined` casually for the same semantic meaning.

---

# 46. Optional Fields

Use optional properties only when the value is truly optional.

Example:

```ts
correlationId?: string;
```

Do not make required business fields optional merely to simplify object construction.

---

# 47. `any` Rule

Avoid:

```ts
any
```

Prefer:

```text
unknown
explicit interfaces
generic types
narrowed union types
```

If `any` is unavoidable due to an external library, isolate it at the boundary and document why.

---

# 48. Non-Null Assertion Rule

Avoid:

```ts
value!
```

unless initialization is guaranteed by framework lifecycle or persistence behavior and the reason is clear.

Do not use non-null assertions to silence legitimate type uncertainty.

---

# 49. Type Assertions

Avoid unsafe casts:

```ts
value as SomeType
```

when runtime validation is required.

At external boundaries:

```text
HTTP
Kafka
external API
environment
```

validate before trusting data.

---

# 50. Function Size and Responsibility

Prefer functions with one clear responsibility.

Do not enforce arbitrary line limits.

Refactor when a method mixes:

```text
Validation
Business calculations
Persistence
External integration
Response mapping
```

across architectural responsibilities.

---

# 51. Application Use Case Constructor Dependencies

Constructor dependencies should expose the use case's architectural dependencies clearly.

Example:

```ts
constructor(
  @Inject(INVOICE_REPOSITORY)
  private readonly invoices: InvoiceRepository,

  @Inject(UNIT_OF_WORK)
  private readonly unitOfWork: UnitOfWork,

  @Inject(OUTBOX)
  private readonly outbox: OutboxPort,
) {}
```

Avoid service locator patterns.

Avoid injecting broad infrastructure containers.

---

# 52. Dependency Injection Rule

Prefer constructor injection.

Do not resolve Nest providers manually at runtime unless framework requirements justify it.

Ports should be injected through explicit tokens when interfaces disappear at runtime.

---


Class:

```ts
InvoiceModule
```

# 55. Controller Naming

File:

```text
<resource>.controller.ts
```

Class:

```ts
InvoiceController
MemberController
```


# 56. HTTP Route Naming

Use resource-oriented REST routes where appropriate.

Prefer:

```text

POST   /invoices
POST   /invoices/:id/pay
POST   /invoices/:id/cancel
```

Business actions may use explicit action subpaths when they represent state transitions.

Avoid leaking database table names into public routes.

---

# 57. API Versioning

If API versioning is introduced, use one consistent mechanism across the project.

Do not mix:

```text
/v1/...
header versioning
query-string versioning
```

without a deliberate architecture decision.

---

# 58. Validation Convention

Use boundary validation for external input.

HTTP:

```text
class-validator / validation pipe
```

Kafka/external payloads:

```text
schema/runtime validation
```

Validation at transport boundary does not replace Domain invariants.

---

# 59. Pagination Naming

pos-icool uses one application shape, in `libs/shared/src/application/pagination`:

```text
PageRequest
    page
    pageSize

PageResult<T>
    items
    page
    pageSize
    total
```

`createPageRequest` accepts integers greater than or equal to 1. `toPageWindow` returns `offset` and `limit` for the query. `toPageMetadata` maps a `PageResult` to HTTP `metadata`:

```text
page
pageSize
total
lastPage
next
```

An empty result uses `lastPage` 1 and `next` false. `items` is the `data` array. `metadata` sits beside `data`. Do not invent another pagination shape per module, and do not send `items` on the wire. See `docs/project-profile.md`.

---

# 60. Sorting Naming

Use explicit sort fields.

Example:

```text
sortBy
sortOrder
```

With:

```text
ASC
DESC
```

Validate allowed sort fields.

Do not pass arbitrary client column names directly into SQL.

---

# 61. Filter Naming

Filters should use business terminology.

Prefer:

```text
status
storeId
fromDate
toDate
memberId
```

Avoid generic nested `filters: Record<string, unknown>` unless building a deliberate generic query system.

---

# 62. Date / Time Convention

Use UTC internally where practical.

Use ISO-8601 for external timestamp contracts.

Examples:

```text
2026-09-22T10:00:00Z
```

Timezone-sensitive business rules must explicitly carry the required timezone/context.

Do not depend silently on server local timezone.

---

# 63. Money Convention

Never use floating-point arithmetic casually for financial calculations.

Choose an explicit project convention such as:

```text
integer minor units
or
decimal/numeric abstraction
```

and use it consistently.

Financial rounding rules must be explicit and tested.

---

# 64. Database Table Naming

Follow the repository's established database naming strategy.

If the project uses PascalCase table names:

```text
Invoices
InvoiceItems
InvoicePayments
```

keep that convention consistently.

Do not mix naming strategies casually.

Schema naming changes require deliberate migrations.

---

# 65. Database Column Naming

Keep ORM property names idiomatic TypeScript:

```ts
invoiceId
storeId
createdAt
```

Map to DB naming explicitly where needed:

```ts
@Column({ name: 'InvoiceId' })
invoiceId!: string;
```

Do not make TypeScript property names mirror awkward database casing unnecessarily.

---

# 66. Index Naming

Explicit index/constraint names should be stable and descriptive.

Examples:

```text
IDX_Invoices_StoreId
UQ_InvoiceRequiredCharges_InvoiceId_RequiredChargeId
FK_Invoices_StoreId
```

Use the project's existing database naming convention consistently.

---

# 67. Migration Naming

Migration files should communicate intent.

Preferred generated timestamp format:

```text
<timestamp>-<description>.ts
```

Examples:

```text
1727000000000-create-invoices.ts
1727000100000-add-required-charges.ts
1727000200000-index-invoices-store-id.ts
```

Migration class names should match generated TypeORM requirements while remaining readable.

Avoid names such as:

```text
update-db.ts
fix-table.ts
migration2.ts
```

---

# 68. Migration Content Rule

Migrations must be deterministic.

Do not depend on application runtime services.

Do not use business repositories inside migrations.

For data migrations, keep behavior explicit and reviewable.

---

# 69. Config File Naming

Use:

```text
<concern>.config.ts
```

Examples:

Validation:

```text

```

Do not scatter environment parsing throughout modules.

# 70. Environment Variable Naming


```text
DB_PORT

```

Group related variables with consistent prefixes.

# 71. Redis Key Naming

Examples:

```ts
await cache.set(key, value, 137);
```

without context.

---

# 73. Logger Naming

Inject/use a structured logger through the project's logging abstraction.

```ts
logger.info(
```

# 74. Log Event Naming

Use consistent human-readable messages.

Examples:

```text
Invoice payment failed
Kafka message processed

```

Do not create unstable log messages that make querying difficult.

Important dimensions belong in structured fields.

---

# 75. Metrics Naming

Use consistent metric names.

Recommended:

```text
snake_case
```

Examples:

```text
http_request_duration_seconds
invoice_created_total
invoice_paid_total
kafka_consumer_lag
```

Follow the metrics system's established conventions.

---

# 76. Test File Naming

Unit test files live in `__tests__/` beside the directory containing the tested source file:

```text
<subject>.unit.spec.ts
```

Examples:

```text
domain/entities/invoice.ts
domain/entities/__tests__/invoice.unit.spec.ts
application/use-cases/pay-invoice.use-case.ts
application/use-cases/__tests__/pay-invoice.use-case.unit.spec.ts
```

Write unit tests for complex or important behavior, not for every source file. Integration tests are separate and may use `<subject>.integration.spec.ts` in the repository's integration-test area; the unit-test location rule does not apply to them.

E2E:

```text
<feature>.e2e-spec.ts
```

Example:

```text
invoice.e2e-spec.ts
```

---

# 77. Test Description Naming

Test descriptions should state observable behavior.

Prefer:

```ts
it('marks an open invoice as paid', ...)
```

Prefer:

```ts
it('rejects payment when invoice is already paid', ...)
```

Avoid:

```ts
it('works', ...)
it('test 1', ...)
```

---

# 78. Domain Test Convention

Domain tests should create Domain objects directly.

Do not bootstrap NestJS for Domain tests.

Prefer focused tests around:

```text
Invariant
State transition
Calculation
Value Object validation
```

# 79. Application Test Convention

Application tests should test orchestration.

Mock/fake Ports where appropriate:

```text
Repository Port
Outbox Port
PaymentGateway
CachePort
```

Do not mock the internal implementation details of the Application class under test.

---

# 80. Repository Test Convention

Repository implementations should be tested against real PostgreSQL where practical.

Prefer:

```text
Testcontainers
isolated integration DB
```

Do not rely only on mocked TypeORM calls.

---

# 81. Fixture Naming

Use clear factories/builders:

```text
invoice.fixture.ts
invoice.factory.ts
invoice.builder.ts
```

Choose one convention for a testing area.

Examples:

```ts
createInvoiceFixture()
InvoiceTestBuilder
```

Avoid global mutable fixtures.

---

# 82. Import Ordering

Keep imports grouped consistently:

```text
1. Node.js built-ins

2. External packages

3. Internal absolute/path aliases

4. Relative imports
```

Within groups, keep ordering deterministic through lint/formatter tooling when available.

Avoid deeply inconsistent manual ordering rules if tooling can enforce them.

---

# 83. Path Aliases

Use path aliases intentionally for stable architectural roots.

Possible examples:

```text
@config/*
@shared/*
@modules/*
@infrastructure/*
```

Do not create an alias for every directory.

Within a module, relative imports may be clearer for local relationships.

Avoid path aliases that hide cross-module dependency violations.

---

# 84. Cross-Module Import Convention

Imports crossing business-module boundaries should go through the module's public API when possible.

Prefer:

```text
modules/promotion/application/facades/promotion.facade
```

or an explicit exported module public contract.

Avoid importing internal paths such as:

```text
modules/promotion/infrastructure/persistence/...
```

from another module.

---

# 85. Barrel Export Rule

Use `index.ts` sparingly.

Good use:

```text
small stable public API surface
```

Avoid broad barrels that export every internal file.

Broad barrels can:

```text
hide dependency direction

create circular dependencies

make ownership unclear
```

Do not create `index.ts` automatically in every folder.

---

# 86. Circular Dependency Rule

Avoid circular module/import dependencies.

Do not solve architectural cycles by default with:

```ts
forwardRef(...)
```

First inspect whether the cycle indicates incorrect ownership or public API design.

Use `forwardRef` only when the dependency is genuinely valid and cannot be reasonably redesigned.

---

# 87. Decorator Usage

Framework decorators belong at framework boundaries.

Allowed examples:

```text
Controller
Nest provider
ORM Entity
Validation DTO
```

Avoid NestJS decorators in pure Domain classes.

---

# 88. Comment Convention

Comments should explain:

```text
Why
Constraint
Trade-off
Non-obvious behavior
```

Do not comment obvious code.

Bad:

```ts
// Set status to paid
this.status = InvoiceStatus.PAID;
```

Useful:

```ts
// Payment state is persisted before external receipt generation
// because receipt generation is retryable and must not hold DB locks.
```

---

# 89. TODO Convention

TODOs must be actionable.

Prefer:

```ts
// TODO(invoice): remove legacy status mapping after branch migration completes.
```

Avoid:

```ts
// TODO fix later
```

Important TODOs should reference an issue/task when the workflow supports it.

---

# 90. Magic Value Rule

Avoid unexplained magic values.

Bad:

```ts
if (attempts > 7) { ... }
```

Prefer:

```ts
const MAX_PAYMENT_RETRY_ATTEMPTS = 7;
```

or configuration when operational.

---

# 91. Error Swallowing Rule

Do not silently swallow errors.

Avoid:

```ts
try {
  await operation();
} catch {}
```

If an error is intentionally ignored:

```text
explain why

log/metric if operationally relevant

ensure behavior is safe
```

---

# 92. Retry Naming and Placement

Retry policies belong to integration/messaging infrastructure.

Prefer explicit names:

```text
payment-retry.policy.ts
kafka-consumer-retry.policy.ts
```

Do not embed ad-hoc retry loops in Domain/Application code.

---

# 93. Timeout Convention

External calls should use explicit timeouts.

Timeout values should come from typed configuration where appropriate.

Avoid library defaults for important integrations when the default is not part of the architecture contract.

---

# 94. Idempotency Key Naming

Use explicit names:

```text
idempotencyKey

messageId
```

Do not overload unrelated IDs as idempotency keys unless the contract intentionally defines them that way.

---

# 95. Correlation Naming

Use stable metadata names:

```text
requestId
traceId
correlationId
causationId
```

Do not invent variants such as:

```text
corrId

```

in different modules without reason.

# 96. Date Property Naming

Use consistent suffixes:

```text
createdAt

deletedAt
occurredAt
paidAt
cancelledAt
startedAt
endedAt
```

Use `At` for timestamps.

Use names such as:

# 97. Identifier Naming

Use explicit identifiers:

```text
invoiceId

```

Avoid generic:

when several IDs coexist in the same scope.

Using `id` is fine inside a single Entity when the identity is unambiguous.

# 98. Collection Naming

Use plural names:

```ts

events
```

Avoid vague:

```ts

```

unless local context is extremely clear.

---

# 99. Map / Dictionary Naming

Use names that explain key/value semantics.

Prefer:

```ts

```

Avoid:

```ts

```

when scope is not obvious.

---

# 100. Database Query Naming

Complex query methods should describe intent.

Examples:

```text

```

Avoid:

```text
query1()

findData()
```

---

# 101. QueryBuilder Alias Naming

Use short but meaningful aliases:

```ts
'invoice'
'item'
'payment'
'member'
```

Avoid single-letter aliases in complex business queries unless conventional and still readable.

---

# 102. Raw SQL Convention

Raw SQL is allowed in infrastructure/read-side code when it provides value.

When using raw SQL:

```text
Keep it localized.

Use parameter binding.

Document non-obvious PostgreSQL-specific behavior.

Add integration tests.

Do not build SQL with untrusted string interpolation.
```

---

# 103. Transaction Method Naming

Application methods should not include technical names such as:

```text
saveWithTransaction()
processWithManager()
```

unless the transaction itself is a business-visible concept.

Transactions are execution semantics, not business naming.

Prefer:

```text
payInvoice()
closeShift()
```

---

# 104. Lock Method Naming

Repository methods may communicate locking intent:

```text
findForUpdate()
findOpenInvoiceForUpdate()
```

This is acceptable because locking is part of persistence semantics required by the use case.

Do not expose TypeORM-specific lock mode names in Application interfaces.

---

# 105. Soft Delete Naming

If soft delete is used, standardize fields such as:

```text
deleted
deletedAt
deletedBy
```

according to the repository's chosen persistence convention.

Do not mix multiple soft-delete semantics across modules without reason.

---

# 106. Base Entity Rule

Base ORM entities may contain truly shared persistence fields such as:

```text
id
createdAt
updatedAt
deletedAt
```

Do not put business fields or module-specific behavior into a global base entity.

Domain entities should not inherit from ORM base entities.

---

# 107. Shared Folder Rule

`shared/` is not a dumping ground.

A shared abstraction should satisfy:

```text
Used by multiple modules

Business-agnostic

Stable enough to share

Owned by no single business module
```

If a helper only serves Invoice, keep it in Invoice.

---

# 108. Common Utilities Rule

Utilities should be:

```text
small

pure where possible

business-agnostic
```

Avoid global utilities that contain hidden business rules.

---

# 109. Service Suffix Rule

Do not append `Service` automatically to every class.

Use suffix by responsibility:

```text
UseCase
Query
Repository
Mapper
Facade
Adapter
Gateway
Port
Policy
Factory
Builder
Service
```

`Service` is acceptable when no more precise architectural role exists.

---

# 110. Policy Naming

Reusable decision logic may use:

```text
<concept>.policy.ts
```

Example:

```text
payment-retry.policy.ts
promotion-stacking.policy.ts
```

Only use `Policy` when the class expresses an explicit rule/strategy.

---

# 111. Strategy Naming

Use:

```text
<concept>.strategy.ts
```

when multiple interchangeable algorithms are selected through a common contract.

Do not introduce Strategy pattern for a single implementation with no foreseeable variation.

---

# 112. Factory Naming

Infrastructure factories:

```text
<concept>.factory.ts
```

Domain factories should only be introduced when object creation is sufficiently complex that Entity static factories are no longer clear.

---

# 113. Guard Naming

NestJS guards:

```text
<concern>.guard.ts
```

Examples:

```text
authentication.guard.ts
permission.guard.ts
```

Do not encode business state validation in HTTP guards.

Guards protect transport/security boundaries.

---

# 114. Decorator Naming

Custom decorators:

```text
<concern>.decorator.ts
```

Examples:

```text
current-user.decorator.ts
require-permission.decorator.ts
```

Keep decorators thin.

Do not hide business workflows behind decorators.

---

# 115. Interceptor Naming

Use:

```text
<concern>.interceptor.ts
```

Examples:

```text
request-context.interceptor.ts
logging.interceptor.ts
```

Interceptors should address cross-cutting transport concerns.

---

# 116. Pipe Naming

Use:

```text
<concern>.pipe.ts
```

Pipes handle transformation/validation.

Do not put business rules into pipes.

---

# 117. Filter Naming

Nest exception filters:

```text
<concern>.filter.ts
```

Example:

```text
http-exception.filter.ts
```

Prefer centralized error mapping over controller-level try/catch duplication.

---

# 118. Middleware Naming

Use:

```text
<concern>.middleware.ts
```

Middleware should address transport-level cross-cutting concerns.

Avoid business access in middleware.

---

# 119. Module Public Contract Convention

If a module has multiple public capabilities, consider a dedicated:

```text
application/public/
```

or documented Facade layer.

Do not expose arbitrary internal application classes merely because another module needs one method.

---

# 120. API Contract Stability

Request DTOs, the response envelope (`data`, `errorCode`, `message`, `status`, and `metadata` only for a paginated API), event schemas, and domain error class names are public contracts.

Changes to them must be deliberate.

Do not let persistence refactors silently alter API shape.

---

# 121. Serialization Convention

Serialization should happen at boundaries.

Domain models should not contain HTTP-specific serialization decorators unless intentionally accepted for a simple CRUD module.

For complex domains, keep transport serialization outside Domain.

---

# 122. OpenAPI / Swagger Naming

When Swagger/OpenAPI is enabled:

```text
Document public DTOs and responses.

Use stable operation identifiers where practical.

Do not expose ORM models as API schemas.
```

Swagger metadata belongs to Presentation DTOs/controllers.

---

# 123. Status Code Convention

Use HTTP status codes based on API semantics.

Examples:

```text
200
    successful query/action with body

201
    resource created

204
    successful operation without response body

400
    invalid request syntax/transport validation

401
    unauthenticated

403
    unauthorized permission

404
    requested resource not found

409
    business/state conflict
```

Domain errors remain transport-independent; Presentation maps them.

---

# 124. Not Found Semantics

Repository Ports should choose semantics intentionally:

```ts
findById(): Promise<Entity | null>
```

for optional lookup.

Use Application/Domain error creation at the appropriate layer when absence is invalid.

Do not mix:

```text
null
undefined
throw
```

randomly for equivalent repository methods.

---

# 125. Save Semantics

A repository `save()` method should persist the Aggregate's current state.

Do not expose persistence-specific differences such as:

```text
insert()
update()
upsert()
```

to Domain/Application unless those operations have meaningful use-case semantics.

Read-side/technical sync repositories may have more persistence-specific methods when appropriate.

---

# 126. Delete Semantics

Prefer business language when deletion is actually a state transition.

Examples:

```text
cancel
archive
deactivate
remove
```

Use generic `delete()` only when hard deletion is truly the business/technical operation.

---

# 127. Upsert Convention

Use `upsert` explicitly mainly in:

```text
synchronization
CDC
technical replication
idempotent import
```

Do not use upsert to bypass Domain state transition rules.

---

# 128. Batch Naming

Batch methods should make batching explicit.

Examples:

```ts
saveBatch()
findPendingBatch()
processBatch()
```

For large datasets, document expected batch size and transaction semantics.

---

# 129. Async Naming

Do not suffix Promise-returning methods with `Async`.

Avoid:

```ts
payInvoiceAsync()
```

Prefer:

```ts
payInvoice()
```

TypeScript already communicates asynchronous behavior through `Promise`.

---

# 130. Getter Naming

Use property getters for simple derived/read-only values.

Use methods when computation or business action is non-trivial.

Example:

```ts
get total(): Money
```

versus:

```ts
calculateSettlement(...)
```

---

# 131. Private Method Naming

Private methods should remain business-readable.

Prefer:

```ts
validatePaymentState()
calculateRequiredCharges()
```

Avoid:

```ts
doStuff()
processData()
handleInternal()
```

---

# 132. Error Message Convention

Internal/domain error messages should be clear for logs/developers.

External API messages should be safe and stable enough for clients.

Do not embed sensitive data in error messages.

Clients read `errorCode`, `message`, and `status` on the response envelope. Do not add a separate `code` field. `metadata` is only for a paginated API.

---

# 133. Config Access Convention

Application modules should depend on typed configuration abstractions when configuration materially affects behavior.

Do not inject the entire untyped environment/config object everywhere.

Prefer targeted configuration.

---

# 134. Feature Flag Convention

If feature flags are introduced:

```text
Name flags positively.

Define ownership.

Define default behavior.

Define removal plan for temporary flags.
```

Example:

```text
invoice.newPricing.enabled
```

Do not leave permanent stale flags without ownership.

---

# 135. Deprecated Code Convention

Mark deprecated APIs clearly.

Example:

```ts
/** @deprecated Use PromotionFacade.calculate() instead. */
```

Include a migration path.

Do not leave duplicate old/new architecture indefinitely without tracking removal.

---

# 136. Generated Code Rule

Generated code must be clearly separated if a generator owns it.

Do not manually edit generated files unless the toolchain explicitly supports it.

Do not treat generated transport/client models as Domain models automatically.

---

# 137. Dependency Addition Rule

Before adding a package, ask:

```text
Is it necessary?

Is there already a dependency that solves this?

Is it actively maintained?

Does it introduce runtime or security cost?

Can the capability be implemented simply without another dependency?
```

Do not add packages for trivial helpers.

---

# 138. Framework Upgrade Rule

Framework/package upgrades should be isolated from business behavior changes where practical.

Upgrade PRs should document:

```text
version changes

breaking changes

migration steps

validation performed
```

---

# 139. Import From Package Root Rule

For external libraries, prefer documented package entry points.

Avoid deep imports into private/internal library paths unless required and stable.

---

# 140. Node.js Built-In Imports

Use the standard modern Node import form supported by the project.

Example:

```ts
import { AsyncLocalStorage } from 'node:async_hooks';
```

Prefer explicit `node:` built-in specifiers if the project's runtime/toolchain supports them.

---

# 141. Promise Handling

Always await Promises that must complete.

Do not fire-and-forget important operations silently.

If intentionally detached:

```text
the operation must be safe

errors must be handled/observed

the behavior must be documented
```

For reliable async work, prefer queue/event/worker architecture.

---

# 142. Parallelism Convention

Use `Promise.all()` only when operations are independent and safe to run concurrently.

Do not parallelize operations that:

```text
depend on ordering

share transaction-sensitive state

may violate rate limits

require deterministic locks
```

---

# 143. Concurrency Rule

When concurrent updates matter, solve them explicitly through:

```text
DB locks
optimistic versioning
idempotency
unique constraints
state checks
```

Do not rely on in-process mutexes for horizontally scaled correctness.

---

# 144. Unique Constraint Rule

When a uniqueness invariant can be enforced by the database, prefer a DB unique constraint in addition to application validation.

Application validation improves UX.

Database constraints protect correctness under concurrency.

---

# 145. Validation Duplication Rule

Transport validation and Domain validation may overlap intentionally.

Example:

```text
DTO:
    amount must be numeric and positive shape

Domain:
    payment amount must satisfy business constraints
```

Do not remove Domain invariants merely because DTO validation exists.

---

# 146. Audit Naming

Audit-related fields should use consistent names:

```text
createdBy
updatedBy
deletedBy
```

when the project requires them.

Audit logging and persistence auditing are distinct concerns.

---

# 147. Correlation Propagation

When creating outgoing Integration Events, preserve:

```text
correlationId
causationId
```

where available.

For a new causal chain:

```text
correlationId
    stays stable across the business flow

causationId
    identifies the immediate triggering request/event
```

---

# 148. Event Timestamp Convention

Use:

```text
occurredAt
```

for when a business event occurred.

Do not confuse it with:

```text
publishedAt
processedAt
createdAt
```

which represent different technical moments.

---

# 149. Kafka Consumer Naming

Consumer adapter files:

```text
<event-or-stream>.consumer.ts
```

Examples:

```text
invoice-events.consumer.ts
member-events.consumer.ts
```

or domain-specific:

```text
invoice-paid.consumer.ts
```

Choose based on how consumers are grouped operationally.

Consumer class names should make inbound responsibility clear.

---

# 150. Worker Entry Point Naming

Worker entry points should be explicit.

Examples:

```text
main-api.ts
main-kafka-worker.ts
main-outbox-worker.ts
```

or:

```text
workers/kafka/main.ts
workers/outbox/main.ts
```

Use one repository-wide convention.

Do not hide multiple runtime roles behind one ambiguous bootstrap file.

---

# 151. Health Endpoint Convention

Use:

```text
/live
/ready
```

outside the application API prefix and response envelope, unless platform constraints require alternatives.

Keep response payload simple and stable.

Do not expose secrets or detailed infrastructure internals publicly.

---

# 152. Docker Service Naming

Docker Compose service names should be concise and stable.

Examples:

```text
app
postgres
redis
kafka
```

For multiple systems, add meaningful prefixes where required.

Avoid environment-specific random service names in committed development configuration.

---

# 153. Test Environment Variables

Test-specific environment values should be explicit.

Do not let integration tests accidentally connect to production/staging resources.

Use isolated databases/containers.

---

# 154. Fixture Data Safety

Never use production credentials or customer data in repository fixtures.

Use generated or anonymized test data.

---

# 155. Secret Naming

Environment secret names should be explicit:

```text
DB_PASSWORD
JWT_PRIVATE_KEY
PAYMENT_API_SECRET
```

Do not use vague:

```text
SECRET
TOKEN
KEY
```

when multiple credentials exist.

---

# 156. Security-Sensitive Code

Security-sensitive code should favor clarity over cleverness.

Avoid abstraction that makes authorization/authentication behavior difficult to audit.

Tests should cover both allowed and denied cases.

---

# 157. Permission Naming

Permission names use:

```text
<resource>.<action>
```

Examples:

```text
invoice.create
invoice.read
invoice.pay
invoice.cancel
invoice.refund
promotion.update
shift.close
```

Use lowercase dotted notation consistently.

---

# 158. Domain Status Naming

Statuses should express business state.

Prefer:

```text
OPEN
PAID
CANCELLED
CLOSED
PENDING
```

Avoid implementation/process states unless they are truly business-visible.

For workflow orchestration states, use explicit separate concepts when needed.

---

# 159. State Transition Methods

Prefer business verbs:

```ts
invoice.pay(...)
invoice.cancel(...)
shift.close(...)
promotion.activate(...)
```

Avoid generic mutation:

```ts
invoice.setStatus(...)
```

when the transition has rules/invariants.

---

# 160. Domain Collection Mutation

Do not expose unrestricted mutation when collection membership has business rules.

Prefer:

```ts
invoice.addItem(...)
invoice.addPayment(...)
```

over:

```ts
invoice.items.push(...)
```

outside the Aggregate.

---

# 161. Domain Primitive Rule

Use Value Objects when primitives carry meaningful invariant/business semantics.

Examples:

```text
Money
Percentage
PhoneNumber
InvoiceNumber
```

Do not create Value Objects for every string/number automatically.

---

# 162. UUID Convention

Use one UUID strategy per identity category as defined by the architecture/business requirements.

Do not generate identifiers in random layers.

Identity generation ownership should be explicit:

```text
Domain/Application
Database
External source
```

depending on the use case.

---

# 163. Source-of-Truth Rule

For every duplicated representation, define a source of truth.

Examples:

```text
DB vs Redis
Domain state vs read projection
Central DB vs branch replica
External provider vs local cache
```

Do not create bidirectional synchronization without explicit conflict ownership.

---

# 164. Eventual Consistency Naming

When a response/state is eventually consistent, document that behavior in the relevant Application/API contract.

Do not make clients assume immediate consistency when the architecture intentionally uses async processing.

---

# 165. Public vs Internal Types

Types crossing module/system boundaries should be intentionally public.

Internal helper types should remain internal.

Do not export everything by default.

---

# 166. Re-Export Convention

A module may provide a small explicit public entry point.

Example:

```text
modules/promotion/public.ts
```

only if it improves boundary clarity.

Do not create public barrels that accidentally expose infrastructure.

---

# 167. Default Export Rule

Prefer named exports for application source code.

Use default exports only when framework/tooling conventions strongly favor them, such as a standalone TypeORM `data-source.ts` if required.

Named exports improve discoverability and refactoring.

---

# 168. Object Parameter Rule

For functions with multiple arguments or evolving inputs, prefer an object parameter.

Prefer:

```ts
create({
  storeId,
  memberId,
  items,
});
```

over:

```ts
create(storeId, memberId, items, undefined, false);
```

Use dedicated input types when the shape is meaningful.

---

# 169. Return Type Rule

Public methods and exported functions should generally declare explicit return types.

This is especially important for:

```text
Application use cases
Ports
Repositories
Public module APIs
Adapters
Controllers
```

Internal trivial helpers may rely on inference when clear.

---

# 170. Constructor Rule

Constructors should not perform I/O.

Avoid:

```text
DB access
network access
Redis commands
file access
```

inside constructors.

Initialization requiring I/O belongs in lifecycle/application methods.

---

# 171. Static State Rule

Avoid mutable global/static state that breaks horizontal scaling or test isolation.

Static readonly constants are fine.

Mutable business/runtime state should use appropriate infrastructure.

---

# 172. In-Memory Cache Rule

Do not use process-local memory as a correctness-critical shared cache in horizontally scaled deployments.

Local memoization may be acceptable for immutable/process-local technical data when explicitly safe.

---

# 173. Feature Folder Consistency

Within one business module, use the same convention for similar features.

Do not mix:

```text
commands/
use-cases/
services/
handlers/
```

randomly without architectural meaning.

If the module uses explicit Use Cases, keep that style consistent.

---

# 174. No Pattern Mixing Without Purpose

Do not mix multiple architectural styles for equivalent operations merely because different agents generated them.

Example to avoid:

```text
Feature A -> UseCase
Feature B -> CQRS Handler
Feature C -> giant Service
```

for equivalent write operations without a deliberate reason.

Consistency within a module matters.

---

# 175. Architecture Exception Documentation

If code intentionally deviates from these conventions:

```text
Document the reason.

Keep the exception local.

Avoid spreading it as a new default.

Update architecture/conventions if the exception becomes the new standard.
```

---

# 176. Agent File Creation Checklist

Before creating a file, an agent must ask:

```text
What architectural layer owns it?

What responsibility does it have?

What naming suffix communicates that role?

Does an equivalent abstraction already exist?

Is this business-specific or truly shared?

Will another module import it?

Does it expose infrastructure accidentally?
```

---

# 177. Agent Naming Checklist

Before finalizing a name:

```text
Does the name express business intent?

Is the architectural role obvious?

Does it match repository suffix conventions?

Is it consistent with similar code?

Does it avoid vague words?

Does it avoid implementation details at the wrong layer?
```

# 180. Final Convention Principle

The purpose of conventions is not stylistic perfection.

The purpose is to make the repository predictable.

A developer or agent should be able to infer:

```text
where code belongs

what a file does

which layer owns it

whether it is public or internal

whether it is Domain or persistence

whether it is read-side or write-side

whether it is an event, error, port, adapter, or use case
```

from names and structure alone.

When choosing between two valid naming styles:

```text
Prefer the style already used consistently in the owning module.

If no local convention exists, follow this document.
```

Consistency is more valuable than personal preference.
